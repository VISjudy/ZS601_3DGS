# v3 验证诊断输出

## 1. 固定协议

固定验证集合由 `images-val10.txt` 定义，必须是 10 个有效且不重复的相机。新训练在 iteration 0、随后每 5000 步以及最终轮生成诊断；150000 步运行预期有 31 个时间点。断点恢复按真实迭代编号写入新输出目录，不伪造 iteration 0，也不覆盖历史目录。

每 50000 步保存 checkpoint，150000 步运行对应 50000、100000、150000 三个 checkpoint。数量是协议预期，只有实际产物通过回读验证后才能记为完成。

## 2. 每相机输出

- RGB render 与 GT；
- 1σ 彩色高斯椭球图；
- 渲染 z-depth；
- 渲染相机坐标法向；
- LiDAR 伪 GT 深度、法向和各自 valid mask；
- 指标 JSON/CSV 和渲染 manifest。

默认不保存 `geometry.npz`。若实验确需保存，必须在运行配置中显式记录。

## 3. 坐标与颜色

深度统一表示相机坐标 `z-depth`，不是到相机中心的欧氏 range。法向诊断图使用相机坐标法向，分量范围 `[-1,1]`，预览颜色使用 `(n+1)/2` 映射。valid mask 是有效性唯一依据，黑色本身不表示无效。

1σ 椭球图使用每个高斯当前尺度的一倍标准差。图像 manifest 应记录该定义、颜色来源、排序方式、相机参数和代码提交，避免把不同尺度定义的图直接比较。

## 4. 法向黑区检查

每次诊断同时记录有效覆盖率、透明度覆盖率、伪 GT 覆盖率、有效区近黑像素比例、法向长度分布和相邻有效像素点积。初始化出现大片黑色时，依次检查：有效 mask、alpha/覆盖、法向空间转换、符号定向、数值范围和 PNG 编码。

## 5. 运行身份

每个时间点的 manifest 至少包括运行 ID、实验组、迭代、Git commit、数据 manifest 哈希、随机种子、GPU、恢复 checkpoint、10 个相机名单、输出文件与哈希。缺失项明确写为 `null`，不得从目录名推断。

## 6. 完成判断

只有目标迭代、所有计划验证时间点、checkpoint、测试指标、最差 10 相机输出及 Drive 回读证据均存在时，才将正式运行标记为完成。单个实验组完成不能表述为整个对比实验完成。
